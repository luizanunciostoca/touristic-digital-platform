## 4. Owner-backed adapters vs placeholders/fallbacks

### Owner-backed / real delegated boundaries

Current `createAdminDomainAdapters(...)` composes:

- Businesses → `createBusinessAdminAdapter`
- CRM → `createCrmAdminAdapter`
- Affiliates → `createAffiliateAdminAdapter`
- Products → `createProductsAdminAdapter` over Ticketing
- Reservations → `createReservationsAdminAdapter` over Ticketing
- Ticketing → `createTicketingAdminAdapter`
- Orders / Financial / Payments → `createFinancialAdminAdapter`
- Content → `createContentAdminAdapter`
- Destinations → `createDestinationAdminAdapter`

The API is fail-closed when an expected adapter is absent; dashboard module state reports `contract-required` when a domain is not composed.

### Placeholder/fallback risks that remain

1. **Business profile runtime composition**
   - `apps/morro-digital-platform/tooling/business-api.mjs` defaults to an in-memory profile repository when no repository is injected.
   - `dev-server.mjs` currently creates `createBusinessApi({ authApi })` without an explicit durable repository.
   - This is acceptable as a development fallback but is not sufficient evidence for a durable Control Center business-admin owner boundary.

2. **Business directory derivation**
   - `businessesFromUsers(...)` derives part of the business directory from Auth user memberships.
   - This is a projection, not a complete Business owner registry.

3. **Settings**
   - Current settings are local Control Center preferences. There is no claim of server-side platform configuration authority, which is safer than inventing one.
   - Any future system-level settings wave must define an owner boundary first.

4. **System**
   - System is intentionally a projection over platform operations/readiness. It should remain read-only unless a separate governed operations contract is introduced.

## 5. Auth and server-authority findings

### Verified strengths

- Capability enforcement is performed server-side in `admin-api.mjs`.
- Critical User actions require `users.manage`, mutation authorization, step-up and audit.
- User session revocation requires `users.sessions.revoke` and step-up.
- Support Mode separates actor from effective user.
- Critical mutations are denied during Support Mode in the audited flows.
- Financial mutations preserve Financial as monetary authority.
- Production financial effects are explicitly code-blocked in the Control Center orchestration path.
- Adapter absence fails closed instead of silently fabricating owner behavior.

### Remaining authority gaps / redesign items

1. Business profile durability and complete Business owner registry are not proven by the current default runtime composition.
2. CRM and Ticketing need a capability-by-capability review for any admin operation not already covered by the delegated contracts.
3. Settings must not grow into privileged server configuration until an explicit authority model, mutation policy, audit contract and recovery path exist.
4. Any future cross-domain entity 360 aggregation must remain read-side composition only; it must not become a write authority.
