# Chat 7 — Browser Offline Content Cache Evidence

## Scope

This wave adds browser persistence for the already-filtered public/offline CMS snapshot.

It deliberately does not make the Service Worker cache arbitrary APIs.

## Storage strategy

The browser adapter uses a dedicated Cache Storage namespace:

`morro-digital-content-v1`

and an internal same-origin synthetic cache key scoped by destination.

No network request is generated by that key; it is only a Cache Storage identity.

## Write boundary

Before writing, the adapter re-validates the complete snapshot through the Content domain parser.

A snapshot containing a disallowed content kind, malformed timestamp, nested unsupported field, mismatched destination or invalid schema is rejected.

## Read boundary

Cached JSON is parsed as unknown and validated again.

Results are explicit:

- `hit`
- `miss`
- `stale`
- `invalid`

Stale or invalid snapshots are deleted immediately and are never returned as current content.

## Authority boundary

The only data accepted by this adapter is the offline-safe public projection.

Therefore this cache cannot contain:

- offer references;
- time-sensitive event truth;
- reservation state;
- checkout state;
- payment state;
- ticket issuance/check-in state;
- financial authority.

Those remain network/server-authoritative.

## Integration boundary

This adapter does not fabricate a CMS HTTP endpoint. A future production content adapter may save an authoritative public snapshot after a successful online read.

Until such an endpoint exists and is accepted, no background sync or speculative content fetch is introduced.
