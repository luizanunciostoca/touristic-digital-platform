M60 promotes `Partner workspace adapter` from `GAP` to `PASS`. The frozen V1 audit confirmed two active Business-owned behaviors: a workspace summary derived from tutorial-session events and a demo-promotion loop that remains inside the sandbox. V2 now reproduces both without restoring the V1 global/iframe coupling.

`@touristic/business/onboarding-workspace` owns the immutable event vocabulary, normalized session-summary projection, category-aware promotion defaults and sandbox promotion construction. Promotion state is always `environment: "sandbox"`, `publishable: false`, tutorial-only and excluded from Business metrics. The runtime records only the frozen tutorial signals already produced by existing onboarding effects.

The `promotions` step renders an editable demonstration form and persists only `businessDemoPromotion`. The `partner-panel` step builds a workspace snapshot from `businessTutorialEventSummary` and renders that isolated summary. The dashboard action emits an explicit handoff to the existing protected Business dashboard with `requiresAuthentication: true`; no iframe, credential, cookie, CSRF bypass or synthetic Auth session is introduced.

The permanent Workspace Browser Contract proves the full browser loop in Chromium: edited promotion submission, sandbox/non-publishable boundary, event-summary increment, workspace rendering, absence of dashboard iframe and authenticated handoff. Route and Profile Browser import maps were extended for the new package subpath and remain regression targets.

`Business profile behavior` remains `PARTIAL` because production profile persistence breadth is not completed by M60. `Live Business runtime` remains `PARTIAL` because production analytics and other frozen runtime breadth are still incomplete. `Commercial conversion adapter` remains the only Business-owned `GAP`, and Payments/checkout remains separately owned.

## Dependency rule

No Business implementation milestone may introduce its own credential/session/cookie/CSRF logic. Those contracts belong to `FEATURE-0008` and must be consumed through an Auth-owned boundary.

The onboarding workflow session remains product/workflow state only and is not an authentication authority. Its runtime allowlist persists only explicit product/tutorial keys and rejects unrelated fields.

Payment/checkout execution remains owned by `FEATURE-0009`; onboarding may expose a future commercial handoff but must not absorb Payments ownership.
